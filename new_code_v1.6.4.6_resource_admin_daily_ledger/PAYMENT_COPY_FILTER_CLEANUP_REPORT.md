# v1.6.4.2 支付文案、商品过滤与死代码清理报告

## 本次修改

- 用户支付交互文案按用户提供的 Markdown 统一更新。
- 正常支付路径保持不变：进入项目 → 生成待付车票 → 点击立即支付 → 系统自动核验 → 主动通知上车。
- 自动验票模式不再向用户提供手动 VP 入口；历史消息里的旧 VP 按钮会被安全拦截，并引导查询状态或联系小掌柜。
- 同额多票、无待付票恢复、查询状态、取消确认和自动失败页面均沿用原业务处理逻辑，只更新用户文案和按钮名称。

## 购买通知过滤

自动监听器只有在消息同时满足以下条件时才会提取 VP 并向 faka 发起查询：

1. 消息包含 `购买成功！` 或半角感叹号形式 `购买成功!`；
2. 存在 `商品：` 字段；
3. 商品名称去除空白和零宽字符后，以 `车位支付链接` 开头；
4. 存在符合格式的 `订单号：VP...`。

过滤顺序为：购买成功标记 → 商品字段 → 商品前缀/白名单 → VP。其他商品、普通通知、失败通知和无 VP 消息会直接忽略，不会调用 faka 查单。

faka 返回结果仍会继续交叉核对系统单号、已支付状态、人民币金额、商品名称、支付方式和 Telegram 用户 ID，避免只凭购买通知自动绑票。

## 无调用代码清理

本次只删除静态调用链能够确认不会执行的内容，没有删除仍在使用的业务功能：

- 删除 82 个被后续同名定义覆盖、运行时永远不可达的旧函数定义；
- 删除 19 个全项目只有定义、没有任何引用且没有路由装饰器的私有辅助函数；
- 删除 13 个确认没有读取的普通导入；
- 清理重复注释和旧版自动支付文案残留。

清理后再次迭代扫描，未发现“无装饰器、无引用”的私有顶层函数；未发现重复顶层函数定义；未发现普通未使用导入。SQLAlchemy 模型注册等有副作用的导入保留。
